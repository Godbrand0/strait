## What You Are Building

**Strait** is a real-time, reorg-safe tunnel indexer for Hemi Network. It tracks assets moving through Hemi's trust-minimized bridges between three chains:

- **Bitcoin** → **Hemi** (BTC tunneled into Hemi as hBTC)
- **Hemi** → **Bitcoin** (hBTC withdrawn back to native BTC)
- **Ethereum** → **Hemi** (ETH/ERC-20 tunneled into Hemi)
- **Hemi** → **Ethereum** (tunneled assets withdrawn to Ethereum)

The core problem: each tunnel transfer produces events on multiple chains simultaneously, with different finality semantics and no shared identifier in raw form. Strait's job is to ingest all three chains, join related events into a single `TunnelTransfer` record with a complete lifecycle, and serve that data via GraphQL and webhooks.

The critical path is the **join engine** — a state machine that takes raw events from three asynchronous ingestion streams and produces unified, reorg-safe `TunnelTransfer` records.

**Hemi specifics you need to know:**
- Hemi is an EVM-compatible chain (chain ID: 43111 for mainnet, 743111 for testnet)
- Hemi RPC: `https://rpc.hemi.network/rpc` (mainnet), `https://testnet.rpc.hemi.network/rpc` (testnet)
- Hemi uses Proof-of-Publication (PoP) miners who publish commitments to Bitcoin, anchoring Hemi's finality to Bitcoin
- Tunnel contracts live on Hemi and have corresponding contracts on Ethereum
- Bitcoin tunnel deposits go to a custody address watched by Hemi validators; the deposit triggers a Hemi mint
- All Hemi EVM interactions use standard EVM logs — same as Ethereum, use `alloy`

### Step 3: Hemi EVM Ingester

Start with the Hemi ingester (not Bitcoin) because it's the closest to a standard EVM chain and lets you validate the event pipeline before touching Bitcoin complexity.

In `strait-evm/src/ingester.rs`, implement `EvmIngester`:

```rust
pub struct EvmIngester {
    provider: Arc<RootProvider<Http<Client>>>,   // alloy provider
    chain: Chain,
    config: EvmChainConfig,
    tunnel_contract: Address,
    event_tx: mpsc::Sender<RawEvent>,           // sends to join engine

impl EvmIngester {

    pub async fn run(self) -> Result<()>;        // main poll loop, runs forever
    async fn poll_new_blocks(&mut self, from: u64, to: u64) -> Result<()>;
    async fn process_logs(&self, logs: Vec<Log>) -> Result<Vec<RawEvent>>;
    async fn detect_reorg(&mut self, block: &Block) -> Option<ReorgEvent>;

```

Reorg detection: keep a rolling window of the last `confirmation_depth * 2` block hashes. On every new block, check that its `parent_hash` matches the hash you have stored for `block_number - 1`. If it doesn't, you have a reorg — walk backward to find the fork point, emit a `BlockReorg` event, and re-index from there.

Define the tunnel contract ABI in `strait-evm/src/contracts.rs` using alloy's `sol!()` macro. You need at minimum:
- `TunnelMint(address indexed to, address indexed asset, uint256 amount, bytes32 sourceTxid)`
- `TunnelBurn(address indexed from, address indexed asset, uint256 amount, bytes destinationAddr)`

You will need to look up the actual Hemi tunnel contract addresses and ABI from Hemi's documentation or deployed contracts. Use `https://explorer.hemi.xyz` to find the tunnel contracts. Stub the addresses with config values and document exactly where to find them.

**Done when:** The Hemi ingester runs against Hemi testnet, prints structured logs for every tunnel event it observes, and correctly detects and emits reorg events when they occur. Validate with `tracing` output.

### Step 5: Bitcoin Ingester

More complex than the EVM ingesters. Implement `BitcoinIngester` in `strait-bitcoin/src/ingester.rs`:

```rust
pub struct BitcoinIngester {
    client: bitcoincore_rpc::Client,
    watched_addresses: HashSet<BitcoinAddress>,
    config: BitcoinConfig,
    event_tx: mpsc::Sender<RawEvent>,
    tip_tracker: TipTracker,               // rolling window of recent block hashes
}
```

The poll loop:
1. Call `getblockcount` to get current height
2. For each new block up to `current_height - confirmation_depth`:
   a. Call `getblock(hash, 2)` to get full block with transactions
   b. Scan every output of every transaction for watched addresses
   c. Scan `OP_RETURN` outputs for Hemi tunnel metadata (the deposit includes the Hemi destination address in OP_RETURN)
   d. Check every transaction for inputs spending previously-seen tunnel UTXOs (this is the withdrawal signal)
3. Run `detect_reorg()` on every block before processing it

For reorg detection on Bitcoin: store a `HashMap<u64, BlockHash>` of `block_number → block_hash` for the last 30 blocks. On each poll, verify that `getblockhash(n)` still returns the hash you stored for block `n`. If not, find the fork point by walking backward and emit `BitcoinEvent::BlockReorg`.

Parse OP_RETURN data: Hemi deposits include a payload in the transaction's OP_RETURN output that encodes the destination Hemi address. Implement `parse_hemi_op_return(data: &[u8]) -> Option<Address>` to extract it. The exact encoding needs to be confirmed from Hemi's Bitcoin tunnel documentation — add a clear `// TODO: confirm encoding with Hemi docs` comment and implement a reasonable placeholder.

**Done when:** Bitcoin ingester connects to a Bitcoin testnet node (or a regtest instance), detects a test deposit to a watched address, parses the OP_RETURN, and emits the correct `BitcoinEvent::TunnelDeposit`.

### Step 6: The Join Engine

This is the most important crate. `strait-join/src/engine.rs` consumes events from all three ingesters and produces `TunnelTransfer` records.

```rust
pub struct JoinEngine {
    event_rx: mpsc::Receiver<RawEvent>,
    transfer_tx: mpsc::Sender<TunnelTransferUpdate>,   // to store layer
    in_flight: HashMap<TransferKey, InFlightTransfer>,
    reorg_window: VecDeque<ReorgCheckpoint>,
}

// The key that lets us match events across chains
// For BTC routes: bitcoin txid of the deposit
// For ETH routes: ethereum tx hash of the lock
pub enum TransferKey {
    BitcoinTxid(BitcoinTxid),
    EthereumTxHash(TxHash),
}

pub enum TunnelTransferUpdate {
    Created(TunnelTransfer),
    StatusChanged { id: Uuid, new_status: TunnelStatus, updated_at: DateTime<Utc> },
    Retracted { id: Uuid, reason: String, retracted_at: DateTime<Utc> },
    DestinationConfirmed { id: Uuid, destination_tx: ChainTransaction },
    PopProofAdded { id: Uuid, proof: PopProof },
}
```

The state machine per transfer (`strait-join/src/state.rs`):

```
BitcoinEvent::TunnelDeposit observed
    → create InFlightTransfer with status INITIATED
    → wait for HemiEvent::TunnelMint with matching source_txid

HemiEvent::TunnelMint with matching source_txid observed
    → update status to ANCHORED
    → wait for PopProof (optional, enhances confidence)

PopProof covering the Hemi mint block observed
    → update status to FINALIZED

At any point: BitcoinEvent::BlockReorg covering the deposit block
    → emit Retracted update
    → remove from in_flight

At any point: HemiEvent::BlockReorg covering the mint block
    → revert to INITIATED status (mint needs to be re-observed)
```

The matcher (`strait-join/src/matcher.rs`) extracts the `TransferKey` from each event type and looks up the `InFlightTransfer`. The matching logic depends on which data the Hemi tunnel contract includes in its `TunnelMint` log — specifically the `sourceTxid` field. This is the primary join key for BTC routes.

For ETH routes, matching uses the Ethereum lock tx hash embedded in the Hemi mint event.

**Done when:** Unit tests in `strait-join` demonstrate the full state machine for both BTC→Hemi and ETH→Hemi routes, including reorg-triggered retraction.

## Quality Standards — Non-Negotiable

**Error handling**: Every fallible function returns `Result`. Use `thiserror` for library errors in `strait-core`, `anyhow` for `main()` and top-level orchestration. Never `.unwrap()` in library code. Never `.expect()` unless the invariant is truly impossible to violate and the comment explains why.

**Logging**: Every significant state transition emits a structured `tracing` event with relevant fields (transfer ID, chain, block number, status). Use `tracing::instrument` on ingester poll loops. Use `tracing::Span` to correlate events across tasks for a single transfer.

**Testing**: Unit tests live alongside their code in `#[cfg(test)]` modules. Integration tests that require Postgres or a chain node live in `tests/` directories within each crate. The join engine has comprehensive unit tests covering every state machine transition — these do not require a database or chain connection.

**No magic numbers**: Chain IDs, confirmation depths, contract addresses, and timeouts are all config values. Nothing is hardcoded in logic.

**Graceful shutdown**: Every long-running task listens to a `CancellationToken` from the `tokio-util` crate (add it to dependencies). On shutdown signal, ingesters stop polling, the join engine drains its input channel, and the API server stops accepting new connections.
